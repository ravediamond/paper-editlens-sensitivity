Most of the robotic papers currently written are tested either in simulation or on costly rigs (>$20k). Out of the 22 papers we analyzed, only 2 were tested on cheaper rigs (<$5k).
But the question is, do the papers' claims still hold on a cheap rig? That is the question we try to answer in this paper.
For that we re-tested the 37 claims out of 22 recent robotic papers on our cheap rig: an SO-101 and an Nvidia Jetson Orin NX 16 GB (€1,350 in total) and some cloud GPU instance usage ($45).
We set 2 rules for our paper validation: make the bar before any test, from the paper and the code only, and test the cheapest baseline first on the same rows (data).
Here are the results: only 12 out of 37 claims hold, 18 outright fail, and several fail even against the baseline.
Among these failures, we found 3 failure classes:

* Too slow on a smaller GPU
* Judges lose to episode length
* Latents lose to the commanded joints

We consolidated all these tests into one single register at Shisso Robotics.
Everything from this paper, from numbers to code to data, is public and can be replicated.

1 Introduction

There are more and more robotic papers tested in simulation or on costly rigs (above $20k): out of 22 papers, 16 were on these and only 2 on a low-cost rig (under $5k).
Small teams using these low-cost rigs need to basically guess, or validate themselves, the different paper claims on their hardware. The register is there so they don't have to guess anymore and can consult it instead.
In the register, 1 row equals 1 claim in the paper's words, the bar, our result and also the data rows.
These rows come from our write-ups, each published with its data, 29 so far.

Let's take the example of adaptive chunking. The idea is to choose the chunk length from the entropy of sampled chunks. Low entropy means that there is not a lot of uncertainty, so long chunks are okay (during transport, for example), and when entropy is high, short chunks are safer (short at the grasp). The problem is that it takes 20 sampled chunks, and the policy took 4,751 ms per decision against a real-time budget of 298 ms, so it is too slow, as the new chunks need to be ready before the robot runs out of actions to run in the current chunk. But this fails only on our hardware; on a more expensive one it may work fine.

Overall only 12 out of 37 paper claims hold, and several failures are not just near misses: the method loses to a code-based baseline.
And these failures can be categorized into 3 failure classes (which we will see in section 4).

2 How a row is made

There are basically 2 rules to create a row in the register:

Rule 1: A bar should be written only with the paper and the code, and not after the first results (since then the bar will drift to make the results already seen pass).

Rule 2: The cheapest baseline is created and tested first. For example, for a predictor, can it beat a copy-last function (where the next state is equal to the current state)? For a learned latent, can it beat a function using only the commanded joint values (which contain the arm state)? For a success judge, can it beat a function checking only the episode length (which can give lots of information about the outcome)?

More precisely, the goal of rule 2 is to optimize the validation process, as not beating the baseline means that the bar does not matter at all.

The papers chosen for the validation are ones that can actually have a chance on our rig: world models, VLAs, failure monitors, chunking, edge latency. So the failure rate is about this register, not the whole field. But no papers that gave bad numbers were removed from the register; transparency is key in the register.
